title: Lists

All endpoints on this page are Platform API endpoints authenticated with `x-api-key`
(base URL `https://api.tokens.xyz/v2`; see the [Quickstart](/docs/v2/quickstart)).

Every endpoint requires only the default `assets:read` scope. Writes are bound to the
API key's project: the key that creates a list owns it, and only keys from that project
can modify it. Anyone can read any published or unlisted list. Error codes, the provider
lookup budget, and cache windows are on [Rate limits & errors](/docs/v2/rate-limits-and-errors).

**Curated slugs**: `majors`, `currencies`, `lsts`, `rwas`, `etfs`, `metals`, `stocks`. The legacy
aliases `stables` (→ `currencies`) and `xstocks` (→ `etfs`) are accepted wherever a slug is, on
`{slug}` paths and in `lists=`.

## `GET /v2/lists`

The list catalog: every curated list plus every published community list, metadata only.

- **Scope**: `assets:read`
- **Query params**:
  - `limit` (1–500, default 100), `offset` — pagination applies to community lists only. The curated
    set is prepended to page one (`offset=0`) and absent from later pages; `total` is the curated
    count plus the published community count.
  - `mine=true` — your project's own lists instead of the public catalog: **every** status
    (`draft`, `unlisted`, `published`, `archived`), each row carrying `status`, no curated rows, and
    `total` equal to the page length. Use this to drive a management UI, including restore of
    archived lists.

```ts
interface ListsResponse {
    lists: Array<{
        slug: string;
        name: string;
        description: string | null; // curated lists only; null for community lists
        curated: boolean;
        owner: { name: string } | { projectId: string };
        tokenCount: number;
        updatedAt: number | null; // unix ms
        status?: 'draft' | 'unlisted' | 'published' | 'archived'; // only with mine=true
    }>;
    total: number;
}
```

## `GET /v2/lists/{slug}`

One list with hydrated tokens. Curated slugs serve the effective curated membership
(registry ∪ admin-added); community slugs serve `published` **and `unlisted`** lists — unlisted
is hidden from the catalog only, and stays readable by anyone with the link. `draft` and
`archived` lists 404 (`"List not found"`).

- **Scope**: `assets:read`
- **Query params**: `limit` (1–2000, default 500), `offset`

```ts
// Same shape as the v1 variant `advisory` field; see
// /docs/v1/endpoints/asset-by-id#advisories for semantics.
type VariantAdvisory = {
    status: 'caution' | 'compromised' | 'blocked';
    reason: string;
    url: string | null;
    since: number; // unix ms
} | null;

interface V2ListToken {
    mint: string;
    symbol: string | null;
    name: string | null;
    decimals: number | null;
    logoURI: string | null;
    verified: boolean; // an active registry variant exists for this mint
    rank: number;
    advisory: VariantAdvisory; // always present; null when not flagged
    note?: string;
    addedAt?: number;
}

interface ListDetailResponse {
    slug: string;
    name: string;
    description: string | null; // curated lists only; null for community lists
    curated: boolean;
    owner: { name: string } | { projectId: string };
    tokenCount: number;
    updatedAt: number | null;
    tokens: V2ListToken[];
}
```

Mints flagged `blocked` are omitted from `tokens` during hydration (`rank` stays dense) and
`tokenCount` reflects the visible tokens, not the raw membership. `caution` and
`compromised` members are returned with `advisory` populated — treat `compromised` as
do-not-trade in your own UI.

## `GET /v2/lists/tokens`

The composition call — the one request a consuming app makes for its subscribed lists.
Returns the union of the named lists, deduped by mint, each token annotated with which of
the requested lists contains it.

- **Scope**: `assets:read`
- **Query params**:
  - `lists` (**required**): comma-separated slugs, max 10. Curated and community slugs mix freely.
    There is no "all lists" value — apps must name the curators they trust.
  - `limit` (1–2000, default 500), `offset` — pagination over the deduped union.

Unknown, draft, or archived slugs are reported in `notFound` instead of failing the call.
Unlisted lists compose by slug like published ones.

```ts
interface ComposeResponse {
    lists: Array<ListsResponse['lists'][number] & {
        truncated?: true; // membership exceeded the 5000-per-list compose ceiling; the union omits the tail
    }>;
    notFound: string[];
    total: number; // size of the deduped union
    tokens: Array<
        Omit<V2ListToken, 'note' | 'addedAt'> & {
            lists: string[]; // requested slugs containing this mint
        }
    >;
}
```

`blocked` mints are omitted here too, so `total` counts visible tokens only.

## Managing lists

Any API key can create lists — project ownership is the security boundary: every key
on a project (regardless of read scopes) may manage that project's lists, and keys
from other projects get `403` on writes. Caps (env-tunable server-side):
**250 mints per batch call**, **5000 members per list** (`400` with
`details.code: "list_full"` beyond it), **100 lists per project** (`400` with
`details.code: "project_lists_limit"`), and **~50 provider lookups per batch call**
for mints unknown to the registry/token index — over-budget unknowns fail individually
as `unknown_mint` and can be retried in a later batch. Batch adds, single-member `PUT`s and
curator search additionally draw from a per-key provider budget (30 batch-family calls /
120 searches per 10 minutes by default) and return `429` when it is exhausted. The full
`details.code` table is on [Rate limits & errors](/docs/v2/rate-limits-and-errors#list-mutation-codes-detailscode).

**Recommended automation flow**: check the slug, create the list (as `draft` if you want
to load it before anyone sees it), load it with one (or a few) batch calls, publish with
`PATCH { status: 'published' }`, then keep it fresh with individual `PUT`/`DELETE /members/{mint}`
calls as your own filters decide. The [Quickstart](/docs/v2/quickstart#publish-your-own-list) walks
through exactly this with `curl`.

Every mutation returns the affected record so you can update local state without a follow-up read:

```ts
interface ListRecord {
    id: string;
    slug: string;
    ownerProjectId: string;
    name: string;
    status: 'draft' | 'unlisted' | 'published' | 'archived';
    createdAt: number; // unix ms
    updatedAt: number;
}
```

### `GET /v2/lists/check-slug`

Is this slug claimable right now? Lets a curator UI validate before submitting instead of
surfacing a `400` from `POST /v2/lists`.

- **Scope**: `assets:read`
- **Query params**: `slug` (**required**; lower-cased before checking)
- **Not cached** — a slug freed by a delete reads as available immediately.

```ts
type CheckSlugResponse =
    | { slug: string; available: true }
    | { slug: string; available: false; reason: 'invalid' | 'reserved' | 'taken' | 'held' };
```

`taken` covers lists in **any** status (a draft or archived list still holds its slug). `held`
means the slug was released recently and only its previous owner can reclaim it during the
hold-down window — that owner sees `available: true`. The answer is advisory: it can go stale
between check and create, and the create path stays authoritative.

### `POST /v2/lists`

Create a list.

- **Body**: `{ slug, name, status? }`
  - `slug`: globally unique, `^[a-z][a-z0-9-]{2,62}$`. Curated ids, their aliases
    (`stables`, `xstocks`) and route words (`all`, `lists`, `curated`, `tokens`, `search-tokens`,
    `check-slug`) are reserved. Prefix by convention: `ownership-core`.
  - `status`: `draft`, `unlisted`, or `published` (default `published`). `unlisted`
    hides the list from the catalog and `inLists` annotations while the direct
    `GET /v2/lists/{slug}` stays readable by anyone with the link.
- **Returns**: `{ list: ListRecord }`
- **Errors** (`400` with `details.code`): `invalid_slug`, `reserved_slug`, `slug_conflict`,
  `slug_held`, `project_lists_limit`.

### `PATCH /v2/lists/{slug}`

Update `name` (≤ 80 chars), `slug` (rename — the old path stops resolving and is held for this
owner for a 30-day window), or `status` (`draft` | `unlisted` | `published` | `archived`).

- **Body**: `{ slug?, name?, status? }`
- **Returns**: `{ list: ListRecord }`
- **Errors**: `403` when your project does not own the list or it is moderator-locked; slug
  errors as for `POST`.

### `DELETE /v2/lists/{slug}`

Permanently deletes the list and its members, releasing the slug (subject to the owner hold-down
window). Irreversible — `PATCH { status: 'archived' }` is the reversible hide-it option.

- **Returns**: `{ list: ListRecord }` (the deleted record)

### `PUT /v2/lists/{slug}/members/{mint}`

Add or update a member. Body (optional): `{ rank?: number, note?: string }` (`note` ≤ 500
chars). Omitted `rank` appends to the end.

- **Returns**: `{ member: { mint: string; verified: boolean; snapshot: object | null } }`
- Draws from the `batch` provider budget when the mint needs a live lookup.

The mint must resolve somewhere: canonical registry (→ `verified: true`) → our token index →
live provider lookup (metadata snapshotted onto the member). A mint unknown everywhere is
rejected with `400` and `details.code: "unknown_mint"`; a malformed address with
`details.code: "invalid_mint"`.

### `DELETE /v2/lists/{slug}/members/{mint}`

Remove a member. `404` when the mint was not in the list (the body still says `"List not found"`;
branch on the status).

- **Returns**: `{ removed: { mint: string } }`

### `POST /v2/lists/{slug}/members`

Bulk add, max 250 items per call, deduped. Two body shapes, usable together:

- `{ mints: string[] }` — bare addresses, appended in order.
- `{ members: Array<{ mint: string; note?: string }> }` — the CSV shape: row order becomes rank
  order and `note` (≤ 500 chars) lands on the member.

A body with neither key is a `400`. Mints are resolved in bulk (registry → token index → budgeted
provider lookups). Per-mint failures are reported without failing the batch:

```ts
interface BatchAddResponse {
    added: Array<{ mint: string; verified: boolean; snapshot: object | null }>;
    failed: Array<{
        mint: string;
        // Same codes as details.code on single-mint writes; in practice
        // invalid_mint | unknown_mint | list_full.
        error: string;
    }>;
}
```

## `GET /v2/lists/search-tokens`

Curator-assist search: decision support for a list owner choosing which mint to add. This is
**not** a public ranking — it defaults to the strict policy and always returns the suppressed
set with reasons so the curator sees what was filtered and why.

- **Scope**: `assets:read`
- **Query params**:
  - `q` (**required**): symbol, name, or mint address (max 100 chars)
  - `policy` (optional): `strict` (default), `default`, or `degen` — bundles of hard gates +
    score weights. `strict` suppresses low-liquidity/day-old tokens and likely impersonators;
    `degen` shows everything and lets the warnings speak.
  - Gate overrides: the same `minLiquidityUsd`, `minAgeDays`, `minMarketScore`,
    `requireMarketData`, `suppressImpersonation` and `verifiedOnly` flags as
    [`GET /v2/search`](/docs/v2/endpoints/search#policies-and-overrides). `policy` in the
    response stays the preset id; `suppressed` is always returned here.
  - `limit` (1–50, default 10)

This is the curator's view of the same pipeline behind [Search & Resolve](/docs/v2/endpoints/search);
use `/v2/search` for end-user features.

```ts
interface SearchTokensResponse {
    query: string;
    interpretation: { intent: 'mint' | 'ticker' | 'name'; normalizedQuery: string; hadSuspiciousCharacters: boolean };
    policy: string; // the preset id; overrides are applied but not echoed here
    policyVersion: string;
    scoringVersion: string;
    sources: { provider: 'ok' | 'degraded' | 'disabled'; db: 'ok' | 'degraded'; registry: 'ok' };
    latencyMs: number;
    results: Array<{
        mint: string;
        claims: { symbol: string | null; name: string | null; attestations: object[] };
        market: object; // price, liquidityUsd, volume24hUsd, marketCapUsd, holderCount, …
        score: { total: number; components: object };
        reasons: string[];   // e.g. exact_symbol_match, curated_list_member, deep_liquidity
        warnings: string[];  // e.g. possible_impersonation, suspicious_characters, new_token, unverified, advisory_caution
        badges: string[];    // e.g. curated:majors, grade:A
        verified: boolean;
        inLists: string[];   // curated + community lists already containing this mint
    }>;
    suppressed: Array<{
        mint: string;
        symbol: string | null;
        name: string | null;
        liquidityUsd: number | null;
        suppressedBy: string[]; // which policy gates fired, e.g. gate_min_liquidity, gate_advisory_blocked
        warnings: string[];
    }>;
}
```

### Reading the output

- **`reasons`** explain rank: match quality (`mint_match`, `exact_symbol_match`, …),
  curation (`curated_list_member`, `registry_variant`), and market context
  (`market_leader`, `deep_liquidity`, `high_activity`, `established_token`).
- **`warnings`** are the curator's caution signals: `possible_impersonation` and
  `symbol_collision` (claims a symbol a protected token holds), `suspicious_characters`
  (homoglyphs/invisible chars in the claim), `new_token` (younger than 7 days),
  `low_liquidity`, `no_market_data`, `unverified` (not in the registry), `stale_data`,
  `high_bot_volume`, `concentrated_holders`, `weak_market_score` (market score below 40), and
  `advisory_caution` (an operator has attached a `caution` advisory to the mint; the result stays
  ranked). The complete code tables are on [Search & Resolve → Explanation codes](/docs/v2/endpoints/search#explanation-codes).
- **`suppressed`** lists candidates a gate removed (`gate_min_liquidity`, `gate_impersonation`,
  `gate_tombstoned`, …). Re-run with `policy=degen` to see them ranked instead.
- **Advisory gates** fire under **every** policy, including `degen`: `gate_advisory_blocked`
  and `gate_advisory_compromised` suppress mints carrying a `blocked` or `compromised`
  advisory. They are still returned under `suppressed[]` with the code, because this
  endpoint exists to build lists and a curator should see that the mint was rejected and why.
  See [Asset by ID → Advisories](/docs/v1/endpoints/asset-by-id#advisories).
