This page focuses on _how users typically chain endpoints_, not the full response schema.

## Workflow: Search → Canonical asset detail page

Use this when you have a user search box and want to render a token detail page.

1. Search:

```bash
curl -sS "$API_BASE_URL/v1/assets/search?q=solana&limit=5" \
  -H "x-api-key: $API_KEY"
```

2. Pick `results[0].assetId`, then fetch the canonical asset with includes:

```bash
ASSET_ID="solana"
curl -sS "$API_BASE_URL/v1/assets/$ASSET_ID?include=profile,risk,ohlcv,markets" \
  -H "x-api-key: $API_KEY"
```

Why this works well:

- One endpoint can return `profile`, `risk`, `ohlcv`, and `markets` as separate include blocks.
- Includes are best-effort: your UI can render what’s available and degrade gracefully.

## Workflow: Asset reference → canonical asset mapping

Use this when you start from a Solana mint address (wallet holdings, swap input, onchain events), or when you have an alias / `assetId` and want the canonical mapping.

```bash
MINT="So11111111111111111111111111111111111111112"
curl -sS "$API_BASE_URL/v1/assets/resolve?ref=$MINT" \
  -H "x-api-key: $API_KEY"
```

Then branch on the status:

- `200`: use the returned `assetId` to fetch asset data (and optionally includes). It is the canonical grouping slug, or `solana-<mint>` for a registered asset exposed under its own mint id (an approved launch coin, for example).
- `404` with `details.code: "asset_not_registered"`: the mint is not a variant of a registered asset. Do not retry; v1 does not synthesize an asset for it. Wallet holdings and swap inputs are the usual source of such mints, so expect this branch. If you still need identity or market data for the token, add it to a [Token List](/docs/v2/endpoints/lists) (`POST /v2/lists`, then `PUT /v2/lists/{slug}/members/{mint}`) and read it with `GET /v2/lists/tokens?lists={slug}`.

## Workflow: Group wallet balances by canonical asset

Use this when an address has multiple token balances and you want to group variants that represent the same asset, such as USD stablecoins or tokenized Tesla shares.

```bash
MINT="EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v"

curl -sS "$API_BASE_URL/v1/assets/resolve?mint=$MINT" \
  -H "x-api-key: $API_KEY"

curl -sS "$API_BASE_URL/v1/assets/solana-$MINT" \
  -H "x-api-key: $API_KEY"
```

Both calls identify `usd` as the canonical grouping asset. Use that `assetId` as your grouping key, then fetch `/v1/assets/usd/variants` when you need the other mints in the group.

Balances whose mint fails with `404` `asset_not_registered` have no grouping asset in v1. Keep them as their own rows, or track them through a [Token List](/docs/v2/endpoints/lists).

The detail and collection responses can include `asset.stats.volume30dUSD`, a nullable rolling 30-day USD volume sum for the canonical group. Use it directly when populated instead of summing daily candles client-side.

## Workflow: Watchlist snapshots (many mints)

Use this when you have a list of mints and want to render a watchlist quickly.

### Option A: `variant-markets` (query string, max 50)

```bash
curl -sS "$API_BASE_URL/v1/assets/variant-markets?mints=$MINT1,$MINT2,$MINT3" \
  -H "x-api-key: $API_KEY"
```

### Option B: `market-snapshots` (JSON body, max 250)

Both options return per-mint (Solana variant) snapshots; the `market-snapshots` rows come from the same variant market table, falling back to the legacy token table. Canonical figures for the grouping asset (CoinGecko price/market cap, canonical supply) are on `GET /v1/assets/:assetId`.

```bash
curl -sS "$API_BASE_URL/v1/assets/market-snapshots" \
  -H "x-api-key: $API_KEY" \
  -H "content-type: application/json" \
  -d '{"mints":["MINT1","MINT2","MINT3"]}'
```

Practical guidance:

- Use **Option A** for lightweight “is there data cached for these mints?” checks.
- Use **Option B** when you have larger lists and want a single request/response body.
- Neither option fails on an unregistered mint; the row is kept in input order. `variant-markets` returns it with `assetId: null`, `chain: null`, `market: null`, `executionQuality: null`; `market-snapshots` returns `token: null`, `hasMarket: false`. For market data on those tokens, add them to a [Token List](/docs/v2/endpoints/lists) and read `GET /v2/lists/tokens?lists={slug}`.

## Workflow: Market + tickers for a canonical asset

Use this to build “Where can I trade this?” UI.

1. Markets (DEX markets list for a mint of the asset):

```bash
curl -sS "$API_BASE_URL/v1/assets/$ASSET_ID/markets?limit=20" \
  -H "x-api-key: $API_KEY"
```

2. Tickers (exchange tickers; requires an external listing ID for the asset):

```bash
curl -sS "$API_BASE_URL/v1/assets/$ASSET_ID/tickers?limit=20" \
  -H "x-api-key: $API_KEY"
```

## Workflow: “Risk badge” for a mint

Use this when you have a single mint address and want a fast signal.

```bash
curl -sS "$API_BASE_URL/v1/assets/risk-summary?mint=$MINT" \
  -H "x-api-key: $API_KEY"
```

Notes:

- Branch on the status first. `404` with `details.code: "asset_not_registered"` means the mint is not a variant
  of a registered asset: there is no score, and retrying will not change that. Show no badge (or an “unlisted”
  state), and track the token through a [Token List](/docs/v2/endpoints/lists) if you need its data.
- On a `200`, branch on `hasInsufficientData` next. When it is `true` the token is unscored and `grade` is a
  placeholder — show “Insufficient Data”, not the grade.
- Registered mints without a cached market snapshot are scored from a live market read. If that read is
  unavailable you’ll get the same “Insufficient Data” response (a `200`, not an error).
